# Decision Log: Behavioral Analytics Engine (IT23212640)

These are the changes from the proposal made during implementation, with the reason for each. They continue the decision log in proposal Appendix E.

| # | Decision | Proposal said | Reason |
|---|---|---|---|
| D1 | **Fine-tune DistilBERT locally** for the Stage B1 threat signal; drop the paid third-party detection API | "integrate an existing, pre-trained content-moderation/threat-detection service" (Stage B1, budget line) | A cloud API sends raw chat text to a third party, which contradicts the privacy-preserving, local-processing claim. Google Perspective API also shuts down on 31 Dec 2026. Local DistilBERT keeps all text on the device and matches the TAF ("Fine-tune DistilBERT"). |
| D2 | **TF-IDF + logistic regression** added as a second content model | not specified | It gives a classical baseline to compare DistilBERT against, and a CPU fallback so the engine runs without GPU-trained weights. |
| D3 | Jigsaw training split: 80 / 10 / 10. A 10% Jigsaw hold-out plus the Kaggle test set (63,978 labelled rows) feed the **generator pools**, which the content model never sees | Appendix A listed Jigsaw, Davidson and Founta | This keeps the T values in synthetic experiments realistic rather than memorised. Founta was not obtained; Davidson is used instead for cross-domain testing and as a pool of short tweet-style text. |
| D4 | **Combined Hate Speech CSV excluded** | not in proposal | All 24,783 Davidson tweets are inside it, so using both would leak test data into training. |
| D5 | **Target Resolver** added as Stage A2 (reply → @mention → name in session roster → broadcast to channel owner) | not specified | The TPI is defined over (offender, target) pairs, so every message needs a target. The resolution method and its confidence are returned to moderators as evidence. |
| D6 | r and s are **exponentially decayed counters**, not raw counts with a separate recency term | TPI = w₁·log(1+r) + w₂·s + w₃·exp(−λΔt) | With raw counts, a reformed user stays at an elevated tier forever, because only the recency term decays. Decaying the counters themselves makes old incidents fade. Ablation: removing decay lowers PR-AUC from 0.94 to 0.90. |
| D7 | A message counts toward r and s only when it is **hostile** (T ≥ 0.5) | "messages sent to the same target" | Friendly regulars who mention the same person every session must not build up persistence. |
| D8 | Risk model fitted with **non-negative (monotone) logistic regression** | α, β, γ "fitted on the synthetic corpus" | This is a security property: more hostility, repetition or escalation must never lower risk. The unconstrained fit gave γ a small negative value. The monotone fit loses no accuracy (validation PR-AUC 0.959 vs 0.959). |
| D9 | Decay half-life **chosen by grid search** (3, 7, 14, 30 days, no decay) on a separate validation world | λ "controls how quickly historical targeting loses weight" | 30 days gave the best validation PR-AUC. |
| D10 | Tier boundaries set from the validation precision-recall curve: High = max-F1 point; Critical = precision ≥ 0.95; Medium = recall ≥ 0.95 | "calibrated" | Each tier then has an operational meaning that can be explained in the viva. |
| D11 | **Explicit-threat safety override**: if a single message has P(threat) ≥ 0.9, the pair is held at ≥ High for 24 h | not in proposal | A credible threat ("I know where you live") should not wait for persistence evidence. The hold is sticky so the tier does not flicker and re-alert on every message. |
| D12 | **Victim-centric coordinated-harassment alert** (≥ 3 distinct hostile senders to one target within 7 days) | not in proposal | Account rotation (sock-puppets) defeats any per-account history. In the rotation stress test, per-pair detection falls to near zero, but this alert catches 100% of victims (7.8% of other targets also alerted). |
| D13 | **Privacy controls**: HMAC-SHA256 pseudonyms, no message text stored, SQLCipher encryption, retention purge, erasure endpoint | "stored and processed locally", "no PII stored" | These make "privacy-preserving" testable (see `tests/test_engine.py`) and support Sri Lanka PDPA No. 9 of 2022 data-minimisation and erasure duties. |
| D14 | **Adversarial text normalisation** (homoglyphs, zero-width characters, leetspeak, spaced letters, stretching) before scoring | not in proposal | This is a security evaluation of evasion. Normalisation restores recall from 0.56–0.64 to about 0.75 under attack (TF-IDF model). |
| D15 | Escalation velocity v is kept in the engine output but its fitted weight is **γ = 0** | γ to be fitted | On the synthetic data, v adds no signal beyond decayed volume and recency. It is reported honestly as a finding and still shown to moderators as evidence. |
| D16 | Synthetic world: 1,500 viewers, 6 channels, 60 days, 9 personas including hard negatives (banter, burst, roaming troll, reformed) and a hard positive (subtle harasser); 25% mention dropout | Appendix C | This reduces circularity: the generator does not use the TPI formula, and the hard cases test exactly where a count rule or a content-only rule would fail. |
| D17 | **SafeChat Lab**: a test live-chat application (WebSocket rooms, researcher-controlled sessions, persistent study codes, role cards, message bank, bots, labelling, export) and `evaluate_collected.py` | not in proposal; requested by the proposal panel | The panel said success depends on a test messaging app for session tracking and on cross-session data. The app produces a human (plus bot) cross-session dataset in the same schema as the synthetic corpus, so the engine is validated on real sessions and not only on simulation. A lab clock maps sessions run on one day onto streams days apart. See `docs/DATA_COLLECTION_PROTOCOL.md`. |
| D19 | **Session report is built only from engine outputs; ground truth appears only in an optional researcher appendix** | not in proposal | A streamer or moderator using the report would not know role assignments or labels. Building the categories (repeat harasser, explicit threat, burst attacker, troll, coordinated-harassment victim) only from logged engine outputs (T, P(threat), pair tier and risk, hostile-message and hostile-session counts, alerts) keeps the report a faithful picture of what the engine can actually tell them. The comparison with roles and labels is a separate, clearly marked appendix (`include_truth=true`), and a unit test checks that the report never reads assignments or labels without it. |
| D20 | **Label integrity check: conflicting role/manual labels are flagged for review, never changed silently** | not in proposal | In the lab data a harasser's target was re-saved as the room owner after messages had been logged, which silently turned the real harassment pair into a role-derived 0. Corrupt ground truth would bias every metric computed on the collected data. *Save role* now refuses target-based roles without a target, and `/api/admin/label-check` lists positive roles overridden by a manual 0, manual 1 labels on non-harasser roles, and role or target changes after messages were logged. The researcher resolves each one explicitly (use role label / keep manual label / mark reviewed), and every decision is exported with the dataset. |
